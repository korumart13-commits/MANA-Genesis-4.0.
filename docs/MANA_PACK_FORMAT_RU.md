# Формат пакетов MANA XZ — .manapack (версия 1)

Статус: спецификация и исходная реализация в разработке; не считать поддерживаемой функцией до прохождения CI, проверки APK и испытаний на устройстве.

## Назначение

`.manapack` — ZIP-контейнер с собственным расширением для доставки одного или нескольких модулей MANA. Расширение само по себе не является механизмом доверия: доверие задаётся встроенным в приложение публичным ключом подписи. Закрытый ключ выпуска хранится вне репозитория и CI-логов.

## Структура

```
example.manapack
├── META-INF/
│   └── manapack.properties
└── modules/
    └── mana.example/
        └── payload.bin | payload.apk | payload.jar | payload.so | payload.dat
```

Manifest properties:
- `pack.id`, `pack.version`
- `target.device` — точный идентификатор устройства либо `any`
- `target.min_api`, `target.max_api`
- `modules.count`
- Для каждого индекса `module.N.id`, `version`, `entry`, `sha256`, `min_os`, `dependencies`
- `signature` — Base64 ECDSA P-256 / SHA256withECDSA над канонической записью

Каноническая запись UTF-8: строка `MANA-PACK/1`, затем ID пакета, версия, target device, min API, max API; далее модули в лексикографическом порядке ID, поля каждого модуля через `|`: ID, версия, путь, SHA-256 в нижнем регистре, минимальная версия MANA OS, отсортированные зависимости через запятую. Строки разделяются LF. Поле signature в каноническую запись не включается.

## Проверки до применения

1. ZIP entry names: без абсолютных путей, `..`, повторов и неожиданных файлов.
2. Ограничения размера manifest, числа модулей, общего payload и свободного места.
3. Совместимость target device, API и минимальной версии MANA OS.
4. Граф зависимостей: все зависимости присутствуют в пакете или уже установлены.
5. ECDSA-подпись проверяется публичным ключом, заранее доверенным приложением.
6. SHA-256 каждого payload вычисляется при потоковом извлечении; несовпадение блокирует весь пакет.
7. Извлечение идёт во временный каталог приложения; исходные файлы пакета не исполняются.

## Обновление и откат

`ManaModuleInstaller` принимает только объект `VerifiedManaPack`. Для каждого модуля текущий каталог переименовывается в резервный каталог транзакции, новый payload размещается во временном каталоге и активируется переименованием. При исключении активированные новые каталоги удаляются, предыдущие восстанавливаются. Каталоги транзакции удаляются после успеха или отката.

Это транзакция файлового хранилища модулей, а не универсальная установка Android APK. APK-модули должны передаваться Android `PackageInstaller` с системным подтверждением пользователя и проверкой package identity/signing lineage. Из APK нельзя тихо устанавливать системные привилегии, прошивать разделы или менять загрузчик. Для ROM/OTA нужен отдельный подписанный OTA-путь, совместимый с Verified Boot и устройством.

## Совместимость и безопасность

- Нельзя принимать публичный ключ из самого пакета.
- Нельзя использовать test key в production.
- Нельзя понижать rollback index или обходить системные подписи Android.
- Не выполнять payload во время проверки.
- Поддержка сжатия, лимиты ZIP и защита от zip-bomb должны оставаться включёнными.
- Любые действия, меняющие разрешения, роли, данные пользователя или системные разделы, требуют отдельного штатного Android flow и явного согласия.

## Ограничения текущей реализации

Реализация в `os/core` — JVM/core уровень. Она не доказывает интеграцию в пользовательский APK, наличие production release key, корректную работу на Android API 29–36 или восстановление после отключения питания в любой момент транзакции. Для production нужны тесты аварийного завершения процесса/питания, fsync каталога, миграция формата, ротация ключей, anti-rollback хранилище и Android PackageInstaller adapter.
