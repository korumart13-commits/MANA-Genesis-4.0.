# MANA Genesis 4.0 — независимый контроль полноты (Completeness Guard)

**Статус:** обязательный инженерный gate для каждой задачи, изменения исходников, сборки и релиза.  
**Назначение:** не допускать потери ранее согласованных требований, модулей, провайдеров, файлов и этапов проекта.  
**Главный источник требований:** `MANA_GENESIS_4.0_MASTER_FILE_RU.md`. Этот документ — контрольный механизм, а не замена главного файла.

## 1. Обязательное правило для каждой доработки

До изменения файлов исполнитель обязан:

1. Прочитать главный файл проекта и связанные требования/архитектурные документы.
2. Определить затронутые модули, зависимости, API, разрешения, сборки, тесты и документацию.
3. Проверить, какие ранее согласованные требования затрагиваются и что нельзя потерять.
4. Составить список конкретных файлов, которые нужно создать/изменить, и объяснить связь каждого с задачей.
5. Проверить совместимость изменения со всей архитектурой MANA, а не только с одним экраном/классом.
6. Внести изменения согласованно: код + тесты + документация + конфигурация/CI, где применимо.
7. Запустить подходящие проверки и сохранить точные результаты/commit SHA.
8. Провести независимый post-change аудит по этому документу и главному файлу.
9. Если требование не реализовано, пометить его `NOT_IMPLEMENTED`, `BLOCKED` или `NEEDS_DEVICE_TEST`; никогда не выдавать его за готовое.
10. Не закрывать задачу как завершённую, пока нет списка проверок и доказательств.

Нельзя заменять полноценный модуль заглушкой, пустой кнопкой, TODO, фиктивным статусом «готово» или только документацией. Если модуль пока не реализуем, его интерфейс, контракт, причина блокировки и следующий конкретный шаг должны быть явно зафиксированы.

## 2. Контрольный реестр обязательных компонентов

Каждый пункт должен иметь статус и ссылку на код/тест/доказательство. Статусы: `IMPLEMENTED`, `PARTIAL`, `NOT_IMPLEMENTED`, `BLOCKED`, `NEEDS_DEVICE_TEST`.

### Центральное ядро и приложение
- [ ] Один основной продукт MANA и единый MANA Brain; не создавать параллельных несвязанных ассистентов.
- [ ] MANA Brain Core: диалог, планирование, задачи, инструменты, политики, память, отчётность.
- [ ] Единый UI/Launcher, Settings, статус Brain и системных возможностей.
- [ ] One-action setup: идемпотентный, возобновляемый, с итогом READY / READY_WITH_LIMITATIONS / OWNER_ACTION_REQUIRED.
- [ ] Capability registry и профили Core / Local AI / Advanced / Platform.
- [ ] Task journal, фоновой supervisor, восстановление после перезапуска.

### Диагностика и ChatGPT handoff
- [ ] Версионированный MANA diagnostic report: runtime evidence, statuses, Android API/ABI, permission states and known limitations.
- [ ] Allow-list export and redaction tests for API keys, bearer/GitHub tokens, passwords, email, phone numbers and URL secrets.
- [ ] Owner-reviewed JSON/Markdown export through Android Sharesheet and FileProvider with temporary read grants.
- [ ] No claim of direct access to the user's current ChatGPT conversation; manual share is the supported handoff.
- [ ] No module is marked IMPLEMENTED without corresponding runtime/test proof.

### Локальный интеллект и провайдеры
- [ ] Реальный локальный inference runtime, а не имитация загрузки модели.
- [ ] LiteRT-LM как предусмотренный Android runtime; модель Gemma 4 E2B IT — кандидат, фактическая совместимость и производительность измеряются.
- [ ] Проверка модели: лицензия/условия, размер, SHA-256, атомарная установка, реальная загрузка и inference.
- [ ] CPU fallback и GPU backend при поддержке; облегчённая модель для слабых устройств.
- [ ] Офлайн-режим без обязательных облачных ключей.
- [ ] Единый provider router и независимые адаптеры: OpenAI GPT, Anthropic Claude, Google Gemini, xAI Grok; иные провайдеры — через документированный интерфейс.
- [ ] Облачные провайдеры отключены по умолчанию; ключи хранятся безопасно и не попадают в логи/модельные промпты без необходимости.
- [ ] Чёткое различие: локальная база знаний/RAG, обучение навыков и переобучение весов модели.

### Память и знания
- [ ] Зашифрованная долговременная память через Android Keystore.
- [ ] Локальная база знаний, индексация и поиск.
- [ ] Журнал событий и задач, резервное копирование/восстановление.
- [ ] Управляемые импорт, экспорт, просмотр, исправление и удаление данных.
- [ ] Не терять данные при ошибке Keystore/БД; не создавать молча пустую память.

### Голос, аватар и интерфейс
- [ ] Русский голосовой ввод/вывод, управление состояниями микрофона и TTS/STT.
- [ ] Один центральный аватар MANA: согласованный внешний образ; лицо/телосложение/голос постоянны, одежда и аксессуары изменяемы.
- [ ] Анимация речи/эмоций с fallback на устройствах без нужной графики.
- [ ] Тёмно-синяя тема, бренд MANA, Android-подобная навигация.
- [ ] Все UI-кнопки имеют реальное действие и корректные состояния ошибок/недоступности.

### Функциональные модули — ни один не забывать

- [ ] VK integration через официальные API/SDK.

- [ ] Дополнительные модули, уже зафиксированные в главном файле или прежних согласованных требованиях, добавлять в этот реестр при обнаружении, не удалять без явного согласия владельца.

### Безопасная инженерия и обновления
- [ ] Engineering Lab: точный snapshot исходников, ограниченный diff, allowlist путей, проверка секретов/опасных изменений.
- [ ] CI build/test, получение логов с редактированием секретов, ограниченное число повторов.
- [ ] Артефакты, SHA-256, подпись, provenance/SBOM где применимо.
- [ ] Карантин и ревью; никаких самовольных commit в main, merge, install или flash.
- [ ] App Update Manager: проверка сертификата/подписи, staged update, health-check, rollback.
- [ ] Безопасность: least privilege, Android sandbox, TLS, безопасное хранение токенов, fail-closed.
- [ ] Подтверждение владельца для платежей, покупок, сообщений и иных consequential actions.
- [ ] Никаких обходов Android security model, скрытой эскалации, эксплойтов или незаметной установки.

### Платформа и прошивка
- [ ] Универсальное приложение: базовая цель Android 10/API 29+; реальная поддержка по матрице API/ABI/OEM.
- [ ] Эмуляторная матрица API 29, 33, 36 и актуального target.
- [ ] Физические тесты нескольких производителей/классов устройств; RMX5566RU/RE645F/Android 16 — один профиль, не универсальное доказательство.

- [ ] OTA только после device bring-up, подписей, recovery, staged install, health-check и rollback.
- [ ] Не называть APK прошивкой; не прошивать неподтверждённые образы.

## 3. Проверка связности и полноты файлов

Для каждой задачи проверить:
- зависимости Gradle/Android SDK/NDK и совместимость minSdk/compileSdk/targetSdk;
- AndroidManifest, permissions, services, receivers, foreground-service types и runtime permission flows;
- связи UI → Brain → provider/runtime → tool/capability → storage;
- тесты unit/instrumentation/emulator/device;
- workflow CI, артефакты и документацию;
- настройки приватности, лицензии и условия внешних API/моделей;
- миграции данных и обратную совместимость;
- отсутствие дублирующих реализаций, мёртвого кода, неиспользуемых кнопок и ложных статусов.

## 4. Обязательный отчёт после каждого изменения

В ответе по каждой инженерной задаче указывать:

1. **Что изменено:** пути файлов и назначение.
2. **Что сохранено:** затронутые существующие требования и модули.
3. **Что проверено:** точные команды/workflows, тесты и результат.
4. **Что не готово:** список NOT_IMPLEMENTED / BLOCKED / NEEDS_DEVICE_TEST.
5. **Риск регрессии:** какие модули могли быть затронуты и как проверены.
6. **Идентификатор:** ветка и commit SHA.
7. **Следующий шаг:** одна конкретная задача, без перекладывания на владельца ручной сборки десятков файлов.

## 5. Независимый контроль перед закрытием задачи

Контролёр повторно сравнивает:
- запрос владельца;
- главный master-файл;
- этот контрольный реестр;
- фактически изменённые файлы и diff;
- тесты и реальные доказательства.

Если любой пункт пропущен, противоречит master-файлу, не имеет теста там, где он нужен, или ошибочно объявлен готовым — задача остаётся незакрытой. Контролёр не должен принимать на веру собственное заявление исполнителя: проверять исходники, diff, CI и статусы независимо.

## 6. Правило сохранения требований

Новые требования владельца добавляются в главный master-файл и этот реестр. Удаление/ослабление уже согласованного требования возможно только после явного решения владельца. При конфликте документов фиксировать конфликт и разрешать его до изменения кода; не выбирать молча удобную трактовку.

## 7. Честная граница

Этот gate — процедура контроля, а не отдельная запущенная GPT-модель и не гарантия абсолютного отсутствия ошибок. Он уменьшает риск пропусков благодаря обязательному сравнению требований, файлов, diff и тестов. Реальный статус всегда подтверждается артефактами и тестами.
